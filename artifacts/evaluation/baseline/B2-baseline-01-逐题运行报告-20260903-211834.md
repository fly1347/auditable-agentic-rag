### Answer

RAG（检索增强生成）的完整流程主要分为两个阶段：**离线索引阶段**和**在线检索-生成阶段**。

1. **离线索引阶段**：
   - 文档加载：支持多种格式，提取纯文本。
   - 文本分块：将文档切分为较小的文本块（chunk）。
   - Embedding 计算：将文本映射到高维向量空间。
   - 向量存储：将向量写入向量数据库，建立索引。

2. **在线检索-生成阶段**：
   - 用户 Query：用户输入查询。
   - Query Embedding：将查询进行向量化。
   - 向量相似度检索：从数据库中检索最相关的文本块。
   - 构建 Prompt：将查询和检索到的文本块结合。
   - LLM 生成回答：使用大语言模型生成最终答案。
   - 返回结果：将结果返回给用户，并包含来源引用。

以上步骤构成了 RAG 的标准工作流程 [E1]。

### Answer

Multi-AZ 部署通过以下方式降低系统单点故障风险：

1. **故障隔离**：每个可用区（AZ）是独立的故障域，若一个 AZ 发生故障，其他 AZ 的副本不受影响，服务可以自动切换到健康的副本，从而保持系统的可用性 [E1]。

2. **同步复制**：数据库在写入时会同步复制到多个 AZ 的副本，确保在故障切换时数据不会丢失，恢复点目标（RPO）接近于零 [E1]。

3. **负载均衡**：负载均衡器将请求分发到多个 AZ 中的健康实例，确保在单个 AZ 故障时流量能够自动切换，用户体验不受影响 [E1]。

4. **Pod 反亲和性和均匀分布**：通过强制 Pods 跨 AZ 分布，确保任一 AZ 故障只影响该 AZ 的 Pods，避免单点故障 [E2]。

这些机制共同作用，显著提高了系统的高可用性和容错能力。

### Answer

HNSW 和 IVF 向量索引的主要区别在于它们的结构和工作原理：

1. **数据结构**：
   - HNSW 使用基于图的结构，通过构建多层邻近图来进行搜索，适合高维数据和低延迟查询 [E3]。
   - IVF 则通过聚类将向量空间划分为多个“桶”，查询时只在最相似的几个桶内进行精确搜索 [E3][E5]。

2. **检索速度与精度**：
   - HNSW 提供极快的检索速度和较高的召回率，但内存占用较大 [E3]。
   - IVF 通过缩小搜索范围来提升检索速度，适合大规模数据集，但召回率不是100% [E3][E5]。

3. **内存占用**：
   - HNSW 通常占用更多内存，因为其图结构需要更多的空间 [E4]。
   - IVF 及其变体（如 IVFPQ）在内存使用上更为高效 [E4]。

4. **构建速度**：
   - IVF 的构建速度通常比 HNSW 快 [E5]。

综上所述，HNSW 更适合对查询延迟有严格要求的场景，而 IVF 则在处理大规模数据时表现更佳。
