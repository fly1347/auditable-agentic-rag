### Answer

RAG（检索增强生成）的完整流程主要分为两个阶段：离线索引阶段和在线检索-生成阶段。

1. **离线索引阶段**：
   - 文档加载：支持多种格式，提取纯文本。
   - 文本分块：将文档切分为较小的文本块（chunk）。
   - Embedding 计算：将文本映射到高维向量空间。
   - 向量存储：将向量写入向量数据库，建立索引。

2. **在线检索-生成阶段**：
   - 用户 Query：用户输入查询。
   - Query Embedding：将查询进行向量化。
   - 向量相似度检索：从数据库中检索最相关的文本块。
   - 构建 Prompt：将查询和检索到的文本块结合。
   - LLM 生成回答：使用大语言模型生成最终答案。
   - 返回结果：将结果返回给用户，并包含来源引用 [E1]。

### Answer

固定长度分块和语义分块的主要区别在于分块的依据和效果：

1. **固定长度分块**（Fixed-size Chunking）是根据固定的字符数或token数进行切分，简单易实现，但可能在语义上切断句子或段落，导致检索精度较差 [E2]。

2. **语义分块**（Semantic Chunking）则是利用自然语言处理技术，根据文本的语义边界进行切分，能够保留语义完整性，减少歧义，适用于需要高语义一致性的场景 [E1][E2]。

因此，固定长度分块更注重实现的简单性，而语义分块则强调语义的连贯性和检索的准确性。

### Answer

Multi-AZ 部署通过以下方式降低系统单点故障风险：

1. **故障隔离**：每个可用区（AZ）是独立的故障域，若一个 AZ 发生故障，其他 AZ 的副本不受影响，服务可自动切换到健康的副本。例如，当 AZ-1 故障时，AZ-2 可以自动提升为主实例，确保服务持续可用 [E1]。

2. **同步复制**：数据库在写入时会同步复制到多个 AZ 的副本，确保数据在故障切换时不会丢失，恢复点目标（RPO）接近于零 [E1]。

3. **负载均衡**：负载均衡器将请求分发到多个 AZ 中的健康实例，单个 AZ 故障时流量会自动切换，用户不会感知到服务中断 [E1]。

4. **Pod 反亲和性和均匀分布**：在 Kubernetes 中，可以通过反亲和性和拓扑分布约束确保 Pods 被调度到不同的 AZ，从而减少单个 AZ 故障对整体服务的影响 [E2]。

这些机制共同作用，显著提高了系统的可用性和容错能力。

### Answer

HNSW 和 IVF 向量索引的主要区别在于它们的结构和工作原理：

1. **数据结构**：
   - HNSW 使用基于图的结构，通过多层邻近图来进行搜索，能够快速定位目标区域并进行精确搜索 [E3]。
   - IVF 则通过聚类将向量空间划分为多个“桶”，查询时只在最相似的几个桶内进行精确搜索 [E3][E5]。

2. **性能与精度**：
   - HNSW 在高维数据和低延迟查询中表现优异，检索速度快且召回率高，但内存占用较大 [E3]。
   - IVF 通过缩小搜索范围提升检索速度，适合大规模数据集，但召回率不是100% [E3][E5]。

3. **构建与内存**：
   - HNSW 的索引构建时间较长，内存占用也较高 [E3][E4]。
   - IVF 的构建速度较快，尤其是其变体（如 IVFPQ）在内存占用上更为节省 [E5]。

综上所述，HNSW 更适合对查询延迟有严格要求的场景，而 IVF 则在大规模数据集的通用场景中表现更好。

2. **集成成本**：pgvector 的集成成本较低，因为可以复用现有的 PostgreSQL 栈；而专用向量数据库需要独立部署和维护。

1. **召回不准（低精度）**：如果检索到的文档片段与用户问题不相关，LLM 将获得噪声上下文，从而生成错误或无意义的回答 [E1]。

   - IVF需要先进行聚类，生成质心后才能建立索引，构建速度较快，但不支持增量插入 [E3]。

4. **适用场景**：
   - IVF适合通用场景，尤其是大规模数据集的高吞吐量需求 [E4]。
   - HNSW更适合对查询延迟有严格要求的应用，如实时推荐和在线搜索 [E4]。

综上所述，IVF和HNSW各有优缺点，选择时需根据具体应用场景的需求进行权衡。
